# Mobile GPS and Website Integration

## 1. Data flow

The app does not send GPS directly to a website URL. The flow is:

```text
Android device GPS + step counter
    -> Google Fused Location Provider
    -> PatrolLocationService
    -> Cloud Firestore
    -> Website Firestore listener
    -> Live map / main dashboard
```

The mobile app writes two Firestore collections:

- `guardLocations/{firebaseAuthUid}`: one document per guard containing the newest location and walking telemetry.
- `locationHistory/{autoId}`: append-only patrol trail points.

For the main live display, the website should read `guardLocations`, not repeatedly query `locationHistory`.

## 2. When GPS tracking starts

Tracking starts only when all of these are true:

1. The guard has granted coarse or fine location permission.
2. The guard starts a patrol.
3. The patrol document exists in `patrol_logs/{patrolLogId}` with `status == "IN_PROGRESS"`.
4. The app has a Firebase Auth UID, site ID, and patrol log ID.

The app starts `PatrolLocationService` from `GuardDashboardActivity`. It is an Android foreground service, so it can continue while the app is in the background, the screen is off, or the guard is using the QR scanner.

The service also listens to the active patrol document. If its status changes from `IN_PROGRESS`, the service stops tracking.

## 3. Five-second GPS and walking updates

The service uses Google Play Services `FusedLocationProviderClient` with:

- Priority: `PRIORITY_HIGH_ACCURACY`
- Requested interval: 5 seconds
- Minimum interval: 5 seconds
- Maximum accepted accuracy: 100 meters

While a patrol is `IN_PROGRESS`, the foreground service writes a heartbeat to
`guardLocations/{firebaseAuthUid}` every **5 seconds**. One heartbeat contains:

- the most recent accepted GPS coordinates;
- the patrol walking total from Android's `TYPE_STEP_COUNTER` sensor;
- tracking state and server timestamp.

This is a fixed publishing cadence, so walking steps continue to reach the
website every five seconds even if the guard is standing still and no new GPS
callback arrives. A GPS coordinate can remain unchanged when the phone has not
received a newer acceptable fix; use `gpsTimestamp` to see the actual age of
the coordinate, and `updatedAt` / `telemetryTimestamp` to see the heartbeat.

GPS delivery is requested every five seconds, but Android, the device GPS and
network availability can delay an actual new fix. The service never invents
coordinates to fill a missed fix.

The latest document write uses:

```text
Collection: guardLocations
Document:   {Firebase Auth UID}
Operation:  set(..., merge=true)
```

The Firestore write is performed in
`PatrolLocationService.publishLivePatrolUpdate()`.

The route history is written separately, at most once every 30 seconds and only after at least 5 meters of movement. The first accepted point is always saved.

On Android 10 and newer, the guard must grant **Physical activity** permission
to read the step counter. If the device has no step sensor or the permission is
not granted, GPS still works and `stepCounterAvailable` is `false`.

## 4. Live document schema

Example document:

```json
{
  "guardId": "firebase-auth-uid",
  "humanGuardId": "G-001",
  "guardName": "Example Guard",
  "siteId": "site-123",
  "siteName": "Main Site",
  "clientId": "client-456",
  "patrolId": "patrol-log-789",
  "patrolLogId": "patrol-log-789",
  "patrolTime": "22:00",
  "latitude": 14.5995,
  "longitude": 120.9842,
  "lat": 14.5995,
  "lng": 120.9842,
  "gpsLat": 14.5995,
  "gpsLng": 120.9842,
  "accuracy": 8.4,
  "speed": 0.7,
  "bearing": 183.0,
  "walkingSteps": 184,
  "stepCounterAvailable": true,
  "telemetryIntervalSeconds": 5,
  "tracking": true,
  "gpsAvailable": true,
  "source": "android-patrol-gps",
  "gpsTimestamp": "Timestamp of the most recent GPS fix",
  "telemetryTimestamp": "Timestamp generated by the phone every 5 seconds",
  "updatedAt": "Firestore server timestamp"
}
```

Use `latitude` and `longitude` as the primary fields. `lat`, `lng`, `gpsLat`, and `gpsLng` are compatibility aliases.

Important fields for the website:

| Field | Meaning |
|---|---|
| `latitude`, `longitude` | Newest accepted GPS coordinates |
| `accuracy` | Estimated accuracy in meters |
| `walkingSteps` | Walking steps since this patrol service started; updated every 5 seconds |
| `stepCounterAvailable` | `true` only if the phone has a usable step sensor and activity permission |
| `gpsAvailable` | `true` after this patrol has received at least one acceptable GPS fix |
| `tracking` | `true` while the patrol service is active; `false` after it stops |
| `updatedAt` | Firestore server time of the five-second heartbeat |
| `telemetryTimestamp` | Timestamp generated on the phone for the five-second heartbeat |
| `gpsTimestamp` | Timestamp of the newest GPS fix; use this to identify a stale coordinate |
| `guardId` | Firebase Auth UID and live-document ID |
| `humanGuardId` | Human-readable guard ID |
| `guardName` | Guard display name |
| `siteId`, `siteName` | Current deployment site |
| `patrolLogId` | Active patrol document ID |
| `source` | Should be `android-patrol-gps` for this tracker |

The website should use `updatedAt` to determine freshness. If `updatedAt` is older than the dashboard's chosen timeout, show the guard as stale/offline even if `tracking` is still `true`.

## 5. Website realtime listener for one guard

The website must authenticate with Firebase and have supervisor access. The simplest listener for a known guard is:

```ts
import { doc, onSnapshot } from "firebase/firestore";
import { db } from "./firebase";

export function watchGuardLocation(
  firebaseAuthUid: string,
  onLocation: (location: {
    latitude: number;
    longitude: number;
    accuracy: number | null;
    walkingSteps: number;
    stepCounterAvailable: boolean;
    gpsAvailable: boolean;
    tracking: boolean;
    updatedAt: unknown;
    gpsTimestamp: unknown;
    guardName: string;
  }) => void,
) {
  const locationRef = doc(db, "guardLocations", firebaseAuthUid);

  return onSnapshot(locationRef, (snapshot) => {
    if (!snapshot.exists()) {
      return;
    }

    const data = snapshot.data();
    const latitude = Number(data.latitude ?? data.lat ?? data.gpsLat);
    const longitude = Number(data.longitude ?? data.lng ?? data.gpsLng);

    if (!Number.isFinite(latitude) || !Number.isFinite(longitude)) {
      return;
    }

    onLocation({
      latitude,
      longitude,
      accuracy: data.accuracy == null ? null : Number(data.accuracy),
      walkingSteps: Math.max(0, Number(data.walkingSteps ?? 0)),
      stepCounterAvailable: data.stepCounterAvailable === true,
      gpsAvailable: data.gpsAvailable === true,
      tracking: data.tracking === true,
      updatedAt: data.updatedAt ?? data.telemetryTimestamp ?? null,
      gpsTimestamp: data.gpsTimestamp ?? null,
      guardName: String(data.guardName ?? "Unknown guard"),
    });
  });
}
```

`onSnapshot()` receives the combined GPS + step update every five seconds while
the phone can reach Firestore. The returned unsubscribe function must be called
when the guard row, map, or page is unmounted.

For example, display the same payload alongside the marker:

```ts
watchGuardLocation(guardUid, (live) => {
  moveGuardMarker(live.latitude, live.longitude);
  setGuardTelemetry({
    steps: live.stepCounterAvailable ? live.walkingSteps : null,
    locationIsFresh: live.gpsAvailable && isRecent(live.gpsTimestamp, 30_000),
    connectionIsFresh: isRecent(live.updatedAt, 15_000),
  });
});
```

Here `isRecent(timestamp, maxAgeMs)` should convert a Firestore `Timestamp`
with `timestamp.toDate()` and compare it with `Date.now()`. It is intentional
that `connectionIsFresh` can be true while `locationIsFresh` is false: this
means the phone is still sending step telemetry but has not obtained a fresh
GPS fix.

## 6. Website listener for all active guards

To display all guards in the main dashboard, listen to the `guardLocations` collection and filter active records:

```ts
import { collection, onSnapshot, query, where } from "firebase/firestore";
import { db } from "./firebase";

const activeGuardsQuery = query(
  collection(db, "guardLocations"),
  where("tracking", "==", true),
);

const unsubscribe = onSnapshot(activeGuardsQuery, (snapshot) => {
  snapshot.docChanges().forEach((change) => {
    const data = change.doc.data();
    const firebaseAuthUid = change.doc.id;

    if (change.type === "removed") {
      removeMarker(firebaseAuthUid);
      return;
    }

    const latitude = Number(data.latitude ?? data.lat ?? data.gpsLat);
    const longitude = Number(data.longitude ?? data.lng ?? data.gpsLng);

    if (!Number.isFinite(latitude) || !Number.isFinite(longitude)) {
      return;
    }

    updateMarker(firebaseAuthUid, {
      latitude,
      longitude,
      guardName: data.guardName ?? "Unknown guard",
      accuracy: data.accuracy ?? null,
      walkingSteps: Math.max(0, Number(data.walkingSteps ?? 0)),
      stepCounterAvailable: data.stepCounterAvailable === true,
      gpsAvailable: data.gpsAvailable === true,
      updatedAt: data.updatedAt ?? data.telemetryTimestamp ?? null,
      gpsTimestamp: data.gpsTimestamp ?? null,
    });
  });
});
```

The website must still remove or mark a marker stale when the last update becomes old. A guard may remain in the query briefly if the phone loses connectivity before it can write `tracking: false`.

## 7. Route history listener

For a patrol trail, query `locationHistory` by patrol ID:

```ts
import {
  collection,
  onSnapshot,
  orderBy,
  query,
  where,
} from "firebase/firestore";
import { db } from "./firebase";

const routeQuery = query(
  collection(db, "locationHistory"),
  where("patrolLogId", "==", patrolLogId),
  orderBy("timestamp", "asc"),
);

const unsubscribe = onSnapshot(routeQuery, (snapshot) => {
  const points = snapshot.docs.map((point) => {
    const data = point.data();
    return {
      latitude: Number(data.latitude ?? data.lat),
      longitude: Number(data.longitude ?? data.lng),
      timestamp: data.timestamp ?? data.deviceTimestamp ?? null,
    };
  });

  drawPatrolRoute(points);
});
```

Firestore may request a composite index for this query. If it does, create the index using the link in the Firebase error message.

## 8. How tracking stops

The app stops the foreground location service when:

- The guard completes or stops the patrol.
- The patrol status is no longer `IN_PROGRESS`.
- The active patrol is invalid or missing.
- Location permission is unavailable.
- The app detects that all required checkpoints were completed.

Before stopping, the service updates:

```text
guardLocations/{firebaseAuthUid}.tracking = false
guardLocations/{firebaseAuthUid}.gpsAvailable = false
guardLocations/{firebaseAuthUid}.patrolLogId = null
guardLocations/{firebaseAuthUid}.trackingStoppedAt = server timestamp
patrol_logs/{patrolLogId}.gpsTracking = false
```

The website should use both `tracking` and timestamp freshness when deciding whether to show a live marker.

## 9. Firestore permissions

The recommended rules currently allow:

```text
match /guardLocations/{id}  {
  allow read: if isSupervisor();
  allow write: if isAuthed();
}

match /locationHistory/{id} {
  allow read: if isSupervisor();
  allow write: if isAuthed();
}
```

Therefore:

- The website user must be signed in with Firebase Authentication.
- The website user must have a supervisor-compatible role in `users/{uid}`.
- The website cannot read live locations anonymously under these rules.
- The Android app can write because it is authenticated.

## 10. Main dashboard implementation checklist

1. Initialize the same Firebase project used by the Android app.
2. Sign the website user in with Firebase Authentication.
3. Verify the user has a supervisor role.
4. Attach an `onSnapshot()` listener to `guardLocations`.
5. Use `latitude` and `longitude` to create or move the map marker.
6. Display `guardName`, `siteName`, `accuracy`, `walkingSteps`, and `updatedAt`.
7. Use `gpsTimestamp` for map-coordinate freshness and `updatedAt` for the five-second telemetry connection.
8. Remove the listener when the dashboard is destroyed.
9. Use `locationHistory` only when drawing a patrol trail or playback.
